# バグ調査ワークフロー スキル

バグ報告をもとに、体系的な手順で原因を特定し、修正方針を立てます。
「推測」ではなく「証拠」に基づいた調査を行います。

## 前提条件

- バグの再現手順または症状が明確であること
- テスト環境でデバッグが可能であること

## 手順

### ステップ 1: バグの理解 📋

1. バグ報告の内容を整理する
   - **症状**: 何が起きているか
   - **期待動作**: 本来どうあるべきか
   - **再現手順**: どうすれば再現できるか
   - **影響範囲**: どの機能・ユーザーに影響するか
   - **発生頻度**: 常時 / 断続的 / 特定条件下

2. 優先度を判定する
   - 🔴 P0: サービス停止・データ損失
   - 🟠 P1: 主要機能が使用不可
   - 🟡 P2: 機能は動作するが不具合あり
   - 🔵 P3: 軽微な不具合・改善

### ステップ 2: 情報収集 🔍

1. 関連するログを確認する
2. エラーメッセージ・スタックトレースを分析する
3. 最近の変更履歴（git log）を確認する
4. 類似のバグが過去に報告されていないか検索する

```bash
# 最近の変更を確認
git log --oneline -20

# 特定ファイルの変更履歴
git log --oneline -10 -- path/to/suspect/file

# 特定の文字列を含む変更を検索
git log -p -S "suspected_keyword" --since="2 weeks ago"
```

### ステップ 3: 仮説の立案 💡

1. 収集した情報をもとに、原因の仮説を3つ以上立てる
2. 各仮説の可能性を評価する
3. 最も可能性の高い仮説から検証する

```markdown
| # | 仮説 | 可能性 | 検証方法 |
|---|------|--------|----------|
| 1 | ... | 高 | ... |
| 2 | ... | 中 | ... |
| 3 | ... | 低 | ... |
```

### ステップ 4: 仮説の検証 🧪

1. 最も可能性の高い仮説を検証する
2. テストコードまたは手動テストで確認する
3. 仮説が正しければステップ5へ、間違っていれば次の仮説を検証

### ステップ 5: 修正方針の決定 🛠️

1. 根本原因を明確に記述する
2. 修正方法を提案する（短期修正 vs 長期修正）
3. 影響範囲を再評価する
4. リグレッションテストの計画を立てる
