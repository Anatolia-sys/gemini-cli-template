# コードリファクタリング スキル

既存コードの品質を向上させるための体系的なリファクタリング手順を定義します。
テストで安全性を担保しながら、段階的にコードを改善します。

## 前提条件

- リファクタリング対象のコードが特定されていること
- テストフレームワークが導入されていること
- バージョン管理（Git）が使用されていること

## 手順

### ステップ 1: 現状分析 📊

1. リファクタリング対象のコードを分析する
2. コードの「匂い（Code Smell）」を特定する
3. リファクタリングの優先順位を決定する

#### よくあるCode Smell一覧

| Code Smell | 症状 | 対処パターン |
|-----------|------|-------------|
| 長い関数 | 50行以上の関数 | Extract Method |
| 巨大なクラス | 多すぎる責務 | Extract Class |
| 重複コード | 同じロジックの繰り返し | Extract Method / Template Method |
| 長いパラメータ | 引数が4つ以上 | Parameter Object |
| Feature Envy | 他クラスのデータを過剰に参照 | Move Method |
| データの塊 | 常にセットで使われる変数群 | Extract Class |
| Switch文の乱用 | 同じ条件分岐の繰り返し | Strategy / Polymorphism |
| コメントだらけ | コードで表現できない処理 | Rename / Extract Method |

### ステップ 2: 安全装置の確保 🛡️

1. 既存テストを実行し、すべてパスすることを確認する
2. テストが不足している場合は、先にテストを追加する
3. リファクタリング前のスナップショットを作成する（コミット）

```bash
# 全テスト実行
npm test              # JavaScript/TypeScript
pytest                # Python
go test ./...         # Go

# リファクタリング開始前にコミット
git add -A
git commit -m "chore: snapshot before refactoring"
```

### ステップ 3: 段階的リファクタリング 🔄

**鉄則: 1回の変更は小さく、テストを通しながら進める**

1. 最も小さな改善から始める
2. 変更を加える
3. テストを実行する
4. パスしたらコミットする
5. 2〜4 を繰り返す

#### リファクタリングパターン早見表

```markdown
## 関数レベル
- Extract Method: 長い関数を小さな関数に分割
- Inline Method: 不要な委譲を解消
- Rename: わかりやすい名前に変更

## クラスレベル
- Extract Class: 責務の分離
- Move Method/Field: 適切なクラスへ移動
- Replace Inheritance with Delegation: 継承を委譲に

## データレベル
- Replace Magic Number with Constant: マジックナンバーの定数化
- Introduce Parameter Object: パラメータのオブジェクト化
- Replace Temp with Query: 一時変数をメソッド呼び出しに
```

### ステップ 4: 検証 ✅

1. すべてのテストがパスすることを確認する
2. 変更前後でコードの可読性が向上したことを確認する
3. パフォーマンスに影響がないことを確認する
4. 最終コミットを行う

### ステップ 5: ドキュメント更新 📝

1. 変更に伴うドキュメントの更新がないか確認する
2. 必要に応じてコメントを追加・更新する
3. PR の説明にリファクタリングの意図を記述する
